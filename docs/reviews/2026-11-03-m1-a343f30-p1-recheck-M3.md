## 五、与 M0 裁定 A 的差异（需 M1 补一步）

M0 11:52 裁定：`BLOCK_OVERLAP` 进入 §5.8 公开闭集；发现重叠时返回
`validation_status=invalid` + 结构化 `violations`，`related_block_ids` 指向双方。

`a343f30` 实际做法（M1 邮件第四节自述，测试也确认）：

```
status=error  code=PROPOSAL_INVALID
details: { reason: BLOCK_OVERLAP, block_ids: [b_0001, b_0021], ... }
```

即走了"用 `PROPOSAL_INVALID` 硬拒"的路径，`BLOCK_OVERLAP` 只是 details 里的一个理由字符串，
不是 violation 条目。差别在于：

- 调用方拿不到 `violations[]` 数组，`related_block_ids` 也不在标准位置；
- 契约 §5.8 明确 `PROPOSAL_INVALID` 是"结构/联合类型错误"路径，用它表达调度硬约束冲突属语义错位；
- 我的核验器按 M0 裁定已把 `BLOCK_OVERLAP` 加入非错误码白名单（本轮同提交），
  若 M1 后续把它放进 `violations[].code`，不会被判"契约外码"。

**所需改动很小**：`check_hard_constraints()` 返回 `invalid` + 一条 `code=BLOCK_OVERLAP` 的 violation，
`related_block_ids=[双方 id]`；`test_block_overlap.py` 的 T2.2–T2.4 断言随之改成
`validation_status=invalid` / `violations[0].code=BLOCK_OVERLAP` / `related_block_ids` 含两个 id。

**影响面**：8 镜录制不经过这条注入路径（镜头 4 走的是正常提案），所以录制本身不被它阻塞；
但它决定"交付的 HEAD 是否就是契约最终形态的 HEAD"。
