## 0. 为什么单列 DA 编号，不并入 T01–T22

M0 v1 契约（`2c48579`）的 7 个工具是 `list_tasks`、`get_calendar_events`、`generate_schedule`、`validate_schedule`、`request_approval`、`get_approval_status`、`apply_approved_changes`——**没有拆解工具**。拆解发生在 Agent 层（模型输出 + 编排），其产物才进入 `generate_schedule` / `validate_schedule`。

因此：

| 项 | 契约验收（T 系列） | 拆解验收（DA 系列） |
|---|---|---|
| 作用对象 | 7 个工具的请求/响应 | Agent 输出的子任务集合与提案 |
| 判定依据 | 契约 §4.1 / §5.7 / §6.x | 本文件 §1 六维判据 |
| 失败归属 | M0 契约或 M1 实现 | Agent 编排（A）/ 调度器（B）/ 提示词 |
| 编号 | T01–T22 | DA01–DA15 |

把拆解断言混进 T 系列会污染契约验收口径：契约没定义子任务结构，任何"拆解不合格"都无法判定是实现缺陷还是契约缺项。**这条边界与矩阵 §0 的纪律一致。**

## 1. 六个质量维度与判据

| 维度 | 判据 | 容差 / 阈值 | 判定方式 |
|---|---|---|---|
| **覆盖率** coverage | 父任务的关键环节齐全，含收尾（校对/格式/提交）；不掺入无关任务 | 收尾环节 ≥1 条 | 子任务名称关键词 + 与父任务语义域比对 |
| **原子性** atomicity | 每条子任务单一可执行、粒度合理；无时间重叠、无语义重复 | 每条 5–90 分钟；条数 4–8；碎片（<5 min）≤2 | 数值区间 + 名称归一化去重 + 区间相交检测 |
| **时长守恒** conservation | Σ 子任务 `estimated_minutes` ≈ 父任务估算 | 360 分钟 ±10% → **324–396** | 求和比对 |
| **依赖有序** ordering | 前置产出排在依赖项之前（查资料→提纲→正文→校对→提交） | 任意依赖对 A→B 满足 `A.end ≤ B.start` | 依赖声明 + 时间序比对 |
| **截止继承** deadline | 子任务与块均不越过父任务截止；模糊表达解析正确 | `child.deadline ≤ parent.deadline` | 字段比对 + 解析结果 weekday/日期校验 |
| **可执行性 / 写入安全** executability | 未确认前零写入；拒绝与沉默都不得落库 | 写入次数 = 0 | override 行数 + `scheduled_at` 逐字段比对 |

**时长守恒的 ±10% 是经验阈值**，不是契约规定。理由：模型估算本身有波动，卡死在 360 会把正常拆解误判为失败；但 480（+33%）与 180（−50%）这种量级必须判失败。

## 3. 四元组在本系列上的适配

矩阵的四元组是「响应码 + Proposal 状态 + 数据结果 + 实际写入次数」。拆解层没有独立错误码，故映射为：

| 四元组槽位 | 拆解层的取值 |
|---|---|
| 响应码 | 正常返回结构化子任务 / `PROPOSAL_INVALID`（拆解产物过不了 validate）/ 澄清追问 |
| Proposal 状态 | `draft`（展示未确认）、`pending_approval`（用户点击确认后）、`rejected`、`expired` |
| 数据结果 | 子任务集合的六维断言（§1） |
| 实际写入次数 | 恒为 0（拆解阶段不写库；写入只发生在 `apply_approved_changes`） |

**DA 系列的写入次数恒 0 是本系列的核心不变量**：拆解与排期是"提案"，不是"执行"。任何 DA 用例出现写入 >0 即为 P0。
