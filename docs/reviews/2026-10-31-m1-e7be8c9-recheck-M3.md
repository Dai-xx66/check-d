## 3. 新发现问题

### F1（P1，实测复现）审批过期记录被永久复用 → 提案锁死

- **现象**：审批记录超过 `expires_at` 后，轮询正确返回 `expired`；但再次调用 `request_approval` 返回**同一条已过期记录**（`expires_at` 仍是过去时间），不会新建。
- **复现**：建提案 → request → 把审批 `expires_at` 改成过去 → 轮询得 `{"status":"expired"}` → 再次 request → 返回同一 `approval_id`，`expires_at=2026-10-01T00:00:00+08:00`。
- **根因**：`request_approval` 的复用条件写的是 `rec.get("status") != "expired"`（`:561`），但代码从不把 `status` 写成 `"expired"`——`expired` 只在轮询时**即时计算**（`:590-591`）并返回，未落库。所以该条件恒为真。
- **后果**：提案一旦审批过期，客户端既拿不到新审批，也无法 apply，**永久锁死**；契约里也没有"重新发起审批"的语义可依。
- **建议**：复用条件改为"未过期"（比对 `expires_at`），或把过期状态落库；并新增用例 T17。

### F2（P1）审批第三态在 `status` 字段上不存在

- **现象**：`get_approval_status` 只有 `pending` / `approved` / `expired` 三值；"刚签发"与"已签发"都是 `approved`，靠 `token` 是否为 null 区分。
- 在这版 mock 里，签发与批准是同一时刻发生的，所以 `approved+null` 语义上确实等于"已签发"；但这是**实现巧合**，不是契约约定。若将来批准与签发分离（真实审批服务必然分离），`approved+null` 将同时表示"已批准待签发"和"已签发"，客户端无法判断能否 apply。
- **建议**：契约中明确 `token_issued` 为独立状态，或规定 `approved` 必须附带 `token_state: issued|not_issued`。

### F3（P1）回读失败时 `proposal_status` 仍是 `applied`，且 `readback_verified` 是常量

- **实测**：注入回读失败 → 返回 `READBACK_MISMATCH`，幂等记录状态 `readback_pending`（正确），但提案表里 `status="applied"`、`applied_proposals` 已包含该 pid；同一幂等键重试 → 仅重试回读、返回成功（正确，无二次写入）；换键重试 → `ALREADY_APPLIED`（合理，说明写入已发生）。
- **问题**：`readback_verified` 在结果字典里是**硬编码 `True`**（`:686`），不是由 `verify_readback` 结果计算。回读失败的那次请求虽然抛了错，但它缓存的 `result` 里仍写着 `readback_verified: True`。
- **契约层影响**：§5.7 的 status 枚举仍无 `readback_pending`，所以客户端从 `proposal_status` 只能看到 `applied`，无法知道"已写但未验证"——这正是 10-29 评审 P0-1 的原始问题，**文档层未解**。

### F4（P2）23:59 封顶会让深夜创建的审批即时过期

- `expires_in_30min()` 用 `time(23, 59)` 封顶，即 `23:59:00`。若在 `23:59:01` 之后创建审批，`min(now+30min, 23:59:00) < now` → **创建即过期**；`23:40` 创建则只有 19 分钟。
- 建议：封顶用 `23:59:59`，并对"剩余不足 N 分钟"给出明确策略（顺延到次日或直接拒绝）。

### F5（P2）`duration_source` 词汇与契约不一致

- 实现两值：`task_target` / `scheduler_estimate`；无 `fallback`，且我的 T12-b 按契约词汇写的是 `task_target` / `snapshot_estimate` / `fallback`。需 M0 统一枚举，否则验收时两边对不上。
