## 一、C 测出来的问题（原话要点）

C 用我 PR #2 head `0f87d4431` 的真实 `repairSchedule` 跑 `scenario_c_meeting_replan`
（15:00–16:30 插入固定会议），结果：

| 指标 | repair | baseline（从零重排） |
|---|---|---|
| 移动块数 | **1** | 4 |
| 总位移（分钟） | **420** | 1505 |
| 冲突 / 重叠 / 未排 / 截止违例 | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 |

他的判词很准：**「最小扰动」只在块数维度成立，位移维度不成立。**
唯一被撞掉的那块（高数第三章习题）从 15:00 挪到 08:00，位移 420 分钟；
而 16:30–17:30 当时是空的，**就近只需 90 分钟**——实际是最优的 4.7 倍。
用户的原话是「其他尽量别动」，把唯一被动的块甩到 7 小时前，跟这句话不符。

根因也确实在实现里：`_placeDemand` 只做「最早可用」，**没有「离原位置最近」的偏好**。

## 二、修复

新增 `_placeNearest(free, demand, input, originStart)`，只在 `repairSchedule` 里对
**上一版已有位置**的块使用；新加入的任务仍走原来的最早可用（它们没有「原位置」可言）。

规则按序：

1. 在同一个空闲片段内，可行起点是连续区间 `[minStart, latestEnd - need]`
   （`minStart` 已并入 `now`、`earliestStartAt`；`latestEnd` 已并入截止）。
   所以**离原位置最近的点**就是把原位置夹进这个区间：`clamp(originStart, minStart, maxStart)`。
2. 跨片段取位移最小的候选；
3. 位移相同时**优先落在原位置之后**（往后顺延比往前甩更符合预期）；
4. 只有**全部候选空档都不可行**时才返回 `null`，由调用方退到最早可用（不会消失、也不会被静默丢弃）。
   若调用方给了 `maxShiftMinutes` 边界，则「边界内无解」同样走这条兜底，见下节。

### 候选空档的搜索边界

M0 要求「说明候选空档的搜索边界」，这里写清楚：

- **候选集**：`free` 里的每一个空闲片段（已扣除固定块、已保留块、`now` 之前的部分），
  以及片段内**每一个可行起点**构成的连续区间 `[minStart, latestEnd - need]`。
  不是只试整点、也不是只试片段起点——整个连续区间都是候选，所以「最近点」是精确的 `clamp`。
- **默认边界：无**。在全部片段里取绝对位移最小的那个。理由：全局最小位移在位置质量上
  **恒定不劣于**最早可用（后者本身就是候选集里的一个点），收紧边界只会让落点变差。
- **可选边界**：`repairSchedule(input, previous, maxShiftMinutes: N)`。
  `N` 非空时，`|候选起点 − 原起点| > N` 的候选不算「合理的局部位置」，被直接排除；
  全部候选都被排除时退最早可用。
- **为什么默认不是某个具体阈值**：阈值属**契约外的调度策略参数**，和 `scheduling_weight`
  一样要由 M0 指位后由服务端传入，M2 不自行发明。默认不设边界，因此服务端不传参时行为
  就是「全局最近」，与已验证的 45 条用例一致。

一个重要的事实（也在邮件里向 M0 说明）：**默认无边界时，「两侧都不可行 → 退最早可用」
这条分支不可达**——`_placeNearest` 只在「任何片段的任何起点都放不下」时返回 `null`，
而那一刻 `_placeDemand`（最早可用）同样放不下，两者可行性判断完全相同。
所以要让这条分支真实可达、并可被测试锁住，必须先把「合理的局部」用边界定义出来。
本轮就是按这个思路加的 `maxShiftMinutes`。

顺带把扰动成本**两维都可读**：

- `REPAIR_SUMMARY` 文案：`共移动 N 处安排，总位移 M 分钟，其余保持不变。`
- `DISPLACED_BY_FIXED` 文案：`…从 15:00 就近移到 16:30–17:30（位移 90 分钟）。`

两个 code 仍在 repair 内部（`ScheduleNote.isPublic == false`），不进 v1 公共 explanations 枚举，
与 `explanations-code-map.md` 的隔离规则一致。

## 四、测试（新增 5 条，总数 40 → 45）

M0 指定的三个分支逐条对应：

| M0 要求的分支 | 用例 | 落点断言 |
|---|---|---|
| 最近可行位置在**原位置之后** | ① `被撞掉的块就近重排：落在原位置之后最近空档，不是最早可用` | 15:00 → **16:30**（+90），显式排除老实现的 11:00 |
| 最近可行位置在**原位置之前** | ③ `就近重排：只有往前才排得下时才往前，不跳到最早可用` | 15:00 → **13:00**（−120），不是 08:00（−420） |
| **两侧都不可行 → 最早可用兜底** | ④ `就近重排：边界内两侧都不可行时退最早可用兜底` | 边界 60 时两侧（+120 / −420）均超界 → **08:00** |
| 平局（附加） | ② `就近重排：位移相同时优先落在原位置之后` | 等距取 **16:00**（+60） |
| 边界不误杀（附加） | ⑤ `就近重排：搜索边界不会误杀界内候选` | 边界 180 时 +120 在界内 → 仍 **17:00** |

用例 ④ 的构造值得单说：同一场景下**默认无边界**落 17:00（位移 +120），
**边界 60** 时落 08:00（位移 −420）。这不是 bug，而是收紧边界的**代价**——
它把「就近」换成了「就在附近，附近没有就按最早可用」。两种行为都锁在同一个用例里，
避免以后有人只改期望值就让测试变绿。

其余两条（①③）的细节：

1. `被撞掉的块就近重排：落在原位置之后最近空档，不是最早可用`
   —— 4 块既有安排（8:00/9:30/13:00/15:00）＋ 15:00–16:30 会议：被撞块必须落 **16:30（位移 90）**，
   且显式排除老实现的 11:00 落点；同时断言其余 3 块 `movedFromPreviousPlan == false`（块数维度不回退）。
   并断言 `DISPLACED_BY_FIXED` 含「位移 90 分钟」、`REPAIR_SUMMARY` 含「总位移 90 分钟」。
3. `就近重排：只有往前才排得下时才往前，不跳到最早可用`
   —— 14:00 之后无空档，前移到 **13:00（−120）**，而不是 08:00（−420）。

## 五、与 C 的验收判据对齐

C 建议的判据是 `nearest_feasible_delta_minutes == actual_delta_minutes`。本实现按**构造**满足它：

- 同一片段内不存在比 `clamp` 结果更近的可行起点——可行起点是连续闭区间，`clamp` 就是区间上的最近点；
- 跨片段取最小，因此全局最近；
- 「等距取之后」「只能往前才往前」两条边界各有独立用例，避免判据在平局处退化成偶然成立。

**需要 C 用他的脚本在新 SHA 上重跑**才能算 E1 闭环——我这边只能证明「落点 = 我算出的最近可行点」，
不能替代他的测量脚本与 fixture。

## 六、边界与遗留

- **不改契约**：未新增/删除任何 explanation code，未改 DTO 字段，未动 §5.7 序列化职责。
- **新增的是内部可选参数，不是对外 API**：`repairSchedule(..., {int? maxShiftMinutes})`，
  默认 `null`（无边界），省略时与旧调用逐字节等价，不影响服务端包装层与 A 轨调用。
  它的**取值**（多大的位移还算「合理局部」）是策略参数，需 M0 指位，M2 不自定。
- **不改 baseline 策略**：`generateSchedule` 仍是「最早可用贪心」，从零重排的位移劣势（1505 分钟）
  是它的固有特征，本轮不优化——C 用它做对照，保持原样才有可比性。
- **未覆盖**：场景 A/B、≥10 条边界用例属 D7；审批与真实日历变化仍是 BLOCKED（A 轨）。
  另外 `scheduling_weight`（§5.2 仍 BLOCKED）的 tie-break 层级同样等 M0 指位。
