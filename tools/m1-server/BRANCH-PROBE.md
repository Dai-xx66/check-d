# 分支关系探针（2026-11-05）

本文件是一次性的分支关系验证探针，**不是业务交付**，验证完成后由 M1 删除或关闭对应 PR。

用途：回应 M0 2026-11-05 09:41:14Z 裁定第一节第 1 条的要求——
用一个无业务影响的最小探针分支，实测「从 upstream `main` 独立起分支，PR 页面会不会带上
PR #3 / #6 / #7 / #8 的 31 个文件改动」。

## 背景

M1 在《M1-PR8 与 P1–P7 实施计划》§1.2 写过一句：

> 「P1/P3/P4/P6/P7 各自从 `main` 起分支、互不依赖……代价是每个 PR 页面都显示 32 files」

M0 指出这句话与 Git 的分支关系存在矛盾：真正从 `main` 当前 head 新建的独立分支，
不应继承其他 PR 的提交，也不应把它们改动的文件带进自己的 diff。

M0 的判断在方向上是对的，M1 那句话把两件不同的事混成了一件：

- **stacked 分支**（PR #7 从 PR #6 head 起、PR #8 从 PR #7 head 起）→ diff 里会带上层提交引入的全部文件；
- **从 `main` 独立起分支** → diff 只含本分支自己的改动。

本探针用来把后者测实，而不是继续用推理说话。

## 探针设计

- 起点：upstream `main` head（SHA 见 PR 描述与交付件）
- 唯一改动：新增本文件（1 个新文件，纯文本，无业务逻辑，无代码依赖）
- 不触碰任何既有文件、不修改 mock、不改任何契约或证据

## 预期与判据

- `git diff --stat <base>...<head>` 期望：**1 file changed, N insertions(+)**
- GitHub PR 页面 Files changed 期望：**1**
- 若结果不是 1（出现 32 files 或混入 PR #3/#6/#7/#8 的改动），则 M1 在计划 §1.2 的
  「代价是 32 files」成立，且 PR-A/C/D/E/F 必须停止批量创建，先报告。
- 若结果为 1，则 M1 §1.2 的那句附带说明**是错的**，PR-A/C/D/E/F 可以从 `main` 正常起分支，
  不必承担「页面显示 32 files」这个代价。
