## 决定点 1：是否同意 request_approval / get_approval_status（工具数 5→7）

**结论：有条件同意。**

这两个工具正确解决了 v1 契约 §7.1 的死结（确认事件如何到达审批服务而不新增"审批即工具"的错觉）：`request_approval` 只创建 pending 请求、不返回 token（`tool_server.py:440-467`）；`get_approval_status` 只在外部确认后才签发（`:470-495`）；"工具调用 ≠ 用户确认"的不变量在两侧都成立。

同意的前提是补三个契约级定义：

1. **`get_approval_status` 的第三态**。token 已签发后再轮询，返回 `status=approved, approval_token=null` + note（`:494-495`）。这是未定义状态：客户端拿到 approved 却没有 token，无法区分"还没取"和"已被取走"。建议把 approval 状态枚举固定为 `pending / approved / token_issued / expired / rejected`，当前实现里 `expired` 会出现（`:478`）但没有代码把它置为 expired，`rejected` 完全不存在。
2. **同一 Proposal 重复 `request_approval` 无幂等约束**（每次生成新 `appr_id`）。多个 pending 审批最终可以各领一个 token。apply 侧有 ALREADY_APPLIED 兜底（见决定点 3 的问题），但契约应写明：同一 proposal 同时至多一个 active 审批请求，重复调用返回原 `approval_id` 或显式错误码。
3. 两工具必须保持 `[候选扩展]` 标记与"非用户确认"声明进入候选契约，不得因为有了它们就宣称审批闭环打通。

## 决定点 2：审批状态与 M2 Proposal 流程的兼容性

**结论：基本兼容，三处需要补。**

- ✅ `request_approval` 前置校验 `status == pending_approval`（`:451`），与 validate 通过后的状态衔接正确；apply 成功置 `applied`（`:557`）。
- ⚠️ **审批记录与 Proposal 状态无双向同步**。`request_approval` 之后 Proposal 被重新校验失败、过期，approval 记录都不会失效；token 签发时不看 Proposal 状态，直到 apply 才在 `:527` 兜住。可接受的防御位置，但契约要写明"签发时不校验、apply 时最终校验"，或者反过来。
- ⚠️ **`expires_at` 硬编码为 `2026-10-30T23:59:00+08:00`**（`:406`、`:462`），今天已过期。Mock 里每个 Proposal 建出来就是过期状态，T06（提案过期）在当前 Mock 上不可测。应参数化。
- ⚠️ `request_approval` 不检查 Proposal 是否已过期，过期提案也能创建审批请求。T06 口径（B3）在 Mock 上无覆盖。

## 决定点 3：错误码、幂等重放与 C 验收口径的一致性

**结论：方向一致，但有 4 个偏差需要修，其中 1 个是死代码。**

| # | 发现 | 证据 | 与 C 口径的关系 |
|---|---|---|---|

## 决定点 4：一次性 token 与"外部确认后才签发"

**结论：同意规则本身，写进候选契约没有障碍；但 Mock 不构成安全证明，以下三点必须保持 BLOCKED。**

1. token 无 TTL、无签名（`:483` 纯 uuid，`tool_apply` 不校验任何过期时间）。"未过期、未撤销"是契约 §6.5 的硬性核验项，Mock 缺失。
2. 审批存储是本地明文 JSON 文件，无访问控制、无签名——**任何能写这个文件的人就是审批者**。作为"外部确认页"的模拟可以，但不能被描述为审批服务。
3. 最关键的一条：`approval_url` 的确认者身份验证仍未解决——谁点确认 = 谁登录，这件事 WorkBuddy 实机上是否可验证，属于 A 的范围且目前 BLOCKED。两扩展解决的是"通道"，不是"信任"。

## 决定点 5：可写入候选契约 vs 保持 BLOCKED

**建议写入候选契约（全部是文档级，不依赖 BLOCKED 能力）：**

1. 7 工具清单，两扩展带 `[candidate]` 标记与"工具调用 ≠ 用户确认"不变量
2. `APPROVAL_CONSUMED`（409）、`ALREADY_APPLIED`（409）写入 §4.1 错误码表
3. approval 状态枚举：`pending → approved → token_issued`；`expired / rejected` 的触发条件
4. token 规则：外部确认后才签发、一次性、绑定 `user + proposal_id + base_version`、apply 成功即消费、**带 TTL 且 apply 时校验**
5. `request_approval` 前置条件：Proposal 处于 `pending_approval` 且未过期；重复请求的幂等行为
6. apply 错误码判定顺序（修正 F1）：幂等缓存 → `ALREADY_APPLIED` → token 状态 → Proposal 状态
7. 幂等摘要定义修正（F4）：绑定 `approval_id`，不含 token 原文
8. `APPROVAL_REQUIRED` 的语义拆分或强制 `details` 区分（F3）

**必须保持 BLOCKED（不能因 18/18 而改口）：**

1. WorkBuddy 实机的确认信号、回调与身份传递（A 的 test-plan 也只是计划，不是实机证据）
2. `approval_url` 确认者身份验证（确认者 = 已登录用户）
3. 审批服务的托管、持久化、防篡改与签名
4. token 的密码学保护与 TTL 强制
5. `APPROVAL_EXPIRED` 全路径（当前零实现）
6. `readback_pending`（B1 依旧 open，Mock 未覆盖）
7. 真实数据库写入、快照版本事务性与 M2 调度器对接
